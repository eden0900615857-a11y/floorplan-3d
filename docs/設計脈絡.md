# 房屋內部裝修模擬系統：設計脈絡

最後更新：2026-09-30　｜　狀態：第十二階段完成，門窗誤判減少

---

## 1. 一句話說明
使用者上傳房屋平面圖，網頁自動產生 3D 模型，接著可以在 3D 裡擺家具、換地板與牆面材質，模擬裝修後的樣子。

## 2. 目標使用者（已決定：一般屋主）
- **屋主／買房族**：想看新家格局、試不同裝潢風格。
- **室內設計師**：快速把客戶的平面圖變成 3D，跟客戶溝通提案。
- **房仲**：把物件平面圖變成可以瀏覽的 3D 給買方看。

不同對象需要的精準度與功能差很多，所以這一題要最先決定。

## 3. 功能範圍

### 第一版（MVP）一定要有
1. 上傳平面圖（JPG / PNG，之後再支援 PDF）。
2. 自動辨識牆，產生 3D 牆體。
3. **2D 校正畫面**：自動辨識一定會有錯，使用者可以拖曳修正牆、刪除多餘的線、補上漏掉的牆。
4. 設定比例尺：點圖上兩點並輸入實際長度（例如 3.5 公尺）。
5. 3D 瀏覽：鳥瞰旋轉、縮放。
6. 存檔、重新開啟專案。

### 第二版
- 自動辨識門、窗，在牆上挖出門窗洞。
- 辨識房間與房名（客廳、臥室…），計算每間坪數。
- 第一人稱室內漫遊。

### 第三版：裝修模擬
- 家具庫：拖曳擺放、旋轉、調整尺寸。
- 更換地板、牆面、天花板材質與顏色。
- 多個裝修方案並排比較。
- 匯出圖片、分享連結、匯出 3D 檔（glTF）。
- 進階：估價清單（依材質面積算材料量）。

### 先不做
- 多樓層、樓梯（除非 Q4 決定要）。
- 結構／水電圖面。
- 手機上的完整編輯（手機先只做瀏覽）。

## 4. 使用流程
```
上傳平面圖
  → 系統自動辨識（牆 → 門窗 → 房間）
  → 2D 校正：確認比例尺、修正牆與門窗
  → 產生 3D 模型
  → 裝修模擬：擺家具、換材質
  → 存檔／分享／匯出
```
關鍵設計：**自動辨識 + 人工校正** 兩段式。不追求 100% 自動，而是讓修正很快。

## 5. 辨識方式比較

| 做法 | 優點 | 缺點 |
|---|---|---|
| A. 傳統影像處理（OpenCV）| 免費、快、可離線、雛形已驗證可行 | 只擅長牆；門窗、房名要另外處理；圖面風格差異大時需調參數 |
| B. 自訓練 AI 模型（分割／物件偵測，公開資料集 CubiCasa5k）| 門窗房間一次辨識、準確度高 | 需要 GPU、訓練與標註成本，台灣圖面風格可能要補資料 |
| C. 多模態 AI API（上傳圖片讓 AI 讀出 JSON）| 開發最快、能讀房名與尺寸文字 | 每次呼叫要費用、座標精準度不穩，需搭配 A 修正 |

**建議**：A 負責牆的精確位置，C 負責讀房名、尺寸標註、門窗大略位置，兩者合併後交給使用者校正。等累積足夠使用者校正過的資料，再考慮 B。

## 6. 系統架構
```
[瀏覽器]
  React 介面
  ├─ 2D 校正編輯器（Canvas / SVG）
  └─ 3D 場景（Three.js / React Three Fiber）
        ↑ 平面圖 JSON
[後端 API]  Python FastAPI
  ├─ 影像處理（OpenCV）
  ├─ AI 辨識（API 或自有模型）
  └─ 專案存取
[儲存]
  資料庫（PostgreSQL 或 Supabase）＋ 檔案儲存（原始圖、家具模型、材質貼圖）
```
- 前端只認「平面圖 JSON」，辨識方法日後怎麼換都不影響 3D 與裝修功能。
- 第一版也可以不做後端：辨識在瀏覽器裡跑（雛形就是這樣），存檔先存在使用者電腦。等要帳號、分享、AI 辨識時再加後端。

## 7. 平面圖 JSON（核心資料格式）
整個系統都圍繞這份資料。單位一律公尺，座標原點在平面圖左上角。

```json
{
  "version": 1,
  "unit": "m",
  "source": { "image": "plan.jpg", "pxPerMeter": 66.2 },
  "walls": [
    { "id": "w1", "a": [0, 0], "b": [12, 0], "thickness": 0.2, "height": 2.8 }
  ],
  "openings": [
    { "id": "d1", "type": "door", "wall": "w1", "offset": 5.3, "width": 0.9, "height": 2.1, "swing": "left" },
    { "id": "n1", "type": "window", "wall": "w1", "offset": 1.2, "width": 1.5, "height": 1.2, "sill": 0.9 }
  ],
  "rooms": [
    { "id": "r1", "name": "客廳", "polygon": [[0,4],[8.5,4],[8.5,7.9],[0,7.9]], "floor": "oak-light" }
  ],
  "furniture": [
    { "id": "f1", "model": "sofa3", "pos": [3.2, 6.8], "rotation": 180, "w": 2.1, "d": 0.9 }
  ],
  "materials": { "wall": "paint-white", "ceiling": "paint-white" },
  "schemes": [
    { "id": "s1", "name": "方案 1", "furniture": [], "materials": { "wall": "paint-white" }, "floors": { "r1": "oak-light" } }
  ],
  "activeScheme": "s1"
}
```
重點：
- 牆存成「中心線 + 厚度」，不是像素。門窗掛在某面牆上：`offset` 是開口中心到牆 `a` 端的距離，移動牆時門窗會跟著走。門的 `hinge` 是門軸靠近牆的 `a` 或 `b` 端，`swing` 是往 a→b 方向的左側或右側開（以螢幕上看到的方向為準）。
- 房間的 `floor` 是地板材質 id（`js/materials.js`：oak-light、oak-dark、tile-white、tile-grey、cement、marble），沒填就用淺色木地板。
- 家具的 `model` 是家具庫的 id（`js/furniture.js`），`pos` 是中心點，`rotation` 是順時針角度（0 度正面朝下），`w`、`d` 是寬和深（公尺）。比例尺縮放時家具只移動位置、不改尺寸。
- `materials.wall` 是牆面顏色 id（paint-white、paint-warm、paint-greige、paint-sage、paint-blue、paint-charcoal）。
- 裝修方案 = 同一份平面圖 + 不同的 `furniture` 與材質設定。平面圖上的 `furniture`、`materials`、房間的 `floor` 永遠是目前方案（`activeScheme`）的內容；`schemes` 保存每個方案的副本（地板依房間 id 對應），存檔時同步，切換時套回。

因為是個人專案、辨識只用影像處理、不需帳號，**第一版可以做成純前端網頁**（辨識在瀏覽器裡跑），不需要後端伺服器，可以免費部署在 GitHub Pages。

### 兩種圖面的比較
- **黑白施工圖**：比較簡單也比較精確。線條乾淨、牆的厚度一致、通常有尺寸標註可以換算比例尺。雜訊主要是尺寸線、軸線和文字，都比牆細，可以用「最小牆厚」濾掉。
- **建商彩色格局圖**：比較難。地板有木紋或磁磚圖案、家具是彩色插圖、有陰影和浮水印，常常沒有標尺寸，而且為了美觀比例不一定準。需要多做一步顏色處理，把「深色、低飽和度」的牆從彩色背景中分出來。
- 一般屋主手上最常有的其實是彩色格局圖，所以它是第二步一定要做的。

## 10. 已知的技術風險
- 圖面風格差異極大，辨識準確度是最大風險，所以校正編輯器是必要功能，不是加分項目。
- 比例尺：有些圖沒有標尺寸，只能靠使用者設定。
- 3D 效能：家具多時手機會卡，需要簡化模型與材質。
- 著作權：使用者上傳的建商圖面，儲存與分享需注意。

## 11. 真實施工圖測試（2026-09-30）
用 Eden 提供的二次施工圖 PDF（A1 圖紙，一張有一樓、二樓、屋頂突出物三張平面圖，加上面積表與圖框，比例 1/100、單位公分）測試：
- 第四階段的圖片辨識幾乎完全失敗：只找到零碎的牆、0 個房間。原因是真實施工圖的**牆是兩條細線畫成的空心牆**，不是範例圖那種塗黑的粗線；圖上還有地界線、退縮線、尺寸線、家具線等大量雜線。
- 這份 PDF 是 CAD 直接輸出的向量圖（約 54 萬段線），也保留了 CAD 圖層，但牆大多不在叫 WALL 的圖層上，所以**不依賴圖層名稱**，改用幾何規則：成對平行線是牆、四分之一圓是門、牆裡的平行細線是窗、小矩形是柱子。
- 結果：一樓找出 4 個空間（客餐廳與廚房、工作室等因為開放通道相連算成一間）、6 扇門、10 扇窗；二樓找出 9 個空間、6 扇門。家具、廚具的平行線偶爾會被當成牆，仍需要 2D 校正。
- 下一步的風險：只用一份施工圖調整過規則。不同事務所的畫法（牆內填斜線、牆畫成實心、門弧畫成折線）可能需要再調整，需要更多真實圖面測試。
- 拍照或掃描的施工圖沒有向量線條，仍然走圖片辨識，也還不支援空心牆，之後可以沿用「成對平行線」的做法。

## 12. 真實建商彩色格局圖測試（2026-09-30）
Eden 提供一張建商彩色格局圖（大理石紋地板、木色櫃子、彩色家具、陰影，約 700 × 491 像素，上緣裁到外牆）。
- 明顯帶顏色的像素只有 4.5%（大理石、灰色家具彩度很低），原本「超過 8% 才自動開彩色模式」沒有開到，辨識結果是一團亂。改成超過 1% 就開（黑白圖彩度是 0，開了也沒有影響）。
- 彩色模式下牆的遮罩相當乾淨，但圖片上緣剛好裁掉外牆，房間封不起來。加上「沿圖片邊緣補牆」後找到 7 個空間：主臥、客餐廳（34.5 m²，比例尺還沒校正）、兩間臥室、兩間衛浴、玄關。
- 入口的門原本被門檻線誤認成窗，改成先找開門弧、再找窗線。
- 還有的問題：餐桌椅的圓弧讓玄關通道多了一扇假門；浴室的一扇窗被當成門；格局圖沒有尺寸標註，比例尺要使用者自己量。

## 13. 分享連結（2026-09-30）
Eden 在第九階段的選項中選了「分享連結」（另外兩個選項是換成真實家具模型、加強辨識，留到之後）。
- 不做帳號也要能給家人看：把平面圖 JSON 用瀏覽器內建的 deflate 壓縮、轉成網址安全的 base64，放在網址 `#v=` 後面。`#` 後面的內容不會送到伺服器，所以網站只是靜態檔案，資料不會上傳。
- 連結不含原圖（檔案太大，建商圖面也有著作權疑慮，見第 10 節），數字只留到公釐。一般的平面圖加兩個方案約 1,200–1,800 個字元，LINE、Email 都傳得了。
- 打開連結是唯讀的瀏覽模式：只顯示 3D、房間清單與材料用量，可以切換方案、漫遊、匯出圖片，不寫入這台電腦的自動保存；按「存到這台電腦來編輯」才會取代原本的平面圖（會先詢問）。
- 連結是當下的快照，之後修改要重新產生。網站用 GitHub Pages 發布（`.github/workflows/pages.yml`），從電腦直接開 `index.html` 時，分享連結會指向網站版。

## 14. 真實家具模型（2026-10-03）
Eden 選了「家具模型」。
- 來源：KayKit Furniture Bits（Kay Lousberg，CC0），低多邊形、單一張 1024 × 1024 漸層貼圖，一件家具約 200–800 個三角形，手機也跑得動。Kenney、Quaternius 等其他 CC0 素材站這次的開發環境連不上，之後可以再補廚具、衛浴。
- 為了從電腦直接開 `index.html`（file://）也能用，不在執行時讀 glTF 檔，而是用 `tools/build-models.js` 把模型壓成 `js/models-data.js`（座標 16 位元、法向量 8 位元、貼圖 data URL，13 個模型約 160 KB），用 `<script>` 載入。
- 模型正規化成 1 × 1 × 1，擺放時依家具的寬、深、高縮放，所以改尺寸時模型會跟著拉長，2D 範圍和 3D 永遠一致。
- 這套模型沒有廚具、冰箱、馬桶、洗手台、浴缸、淋浴間、衣櫃、電視，這些仍用方塊造型。模型顏色是 KayKit 原本的配色（例如橘色沙發），第十一階段加上換色。

## 15. 家具換色（2026-10-03）
Eden 指定下一步做家具換色。
- 存檔格式：家具多一個選用的 `color`（`#rrggbb`），沒有就是原本的顏色。顏色跟著裝修方案、JSON 存檔與分享連結保存。
- 換的是「主色」：模型上面積最大的色塊（貼圖是 8 × 4 格的色塊，相鄰同色的格子算同一塊）。沙發、單人沙發、地毯換布料，床換被子（床架、枕頭不變），桌椅、櫃子換整件木頭，落地燈換燈罩，盆栽換花盆。方塊家具換第一個方塊（櫃體、主體）的顏色。
- 做法：主色的頂點改用貼圖上白到淺灰的漸層色塊，保留原本的明暗，再乘上頂點顏色；其他部分頂點顏色是白色，不受影響。換成木頭色時會失去原本的木紋線條，看起來像上漆的木頭。
- 顏色先提供 12 種固定色（白、米白、淺灰、深灰、黑、原木、胡桃木、灰藍、墨綠、芥末黃、磚紅、乾燥玫瑰），沒有自訂色盤。
- 順便修正：地毯一律畫在其他家具下面，點選時也優先選到上面的家具。

## 16. 辨識加強：門的判斷（2026-10-03）
Eden 要求繼續往下做，選了上次留下的「辨識加強」。用第 12 節的真實彩色格局圖檢查每一個門窗：原本 12 扇門、1 扇窗，其中 5 扇門是假的。
- 原因：判斷門只看「四分之一圓弧上有沒有線」，浴缸、磁磚、櫃子這些密集線條，或餐椅的圓弧，剛好碰到一半以上的取樣點就被當成門。
- 修正一：同時檢查弧的內側、外側（半徑 ±18%）。真的開門弧是一條細線，兩側是空的；弧上的比例要比兩側多 35% 以上。
- 修正二：弧線不完整（取樣點不到 80% 有線）時，還要看得到門片，也就是從門軸垂直牆面畫出去的直線。
- 結果：真實格局圖變成 7 扇門、2 扇窗，逐一對照原圖都正確，浴室外牆的窗也改判成窗。玄關通道沒有門，和客餐廳算成同一間（38.1 m²）。黑白範例、彩色範例、PDF 施工圖的結果不變。
- 還沒解決：這張圖右上的衛浴、右側陽台的牆沒有完全封起來，所以沒有算成房間，要在 2D 校正補牆。

## 17. AI 辨識選項（2026-10-03）
Eden 問能不能用機器學習提高準確度，選了「先試做」，再看過試做結果後選了「加成選項」：上傳圖片時可以選 AI 辨識，原本的規則辨識保留。
- 模型：CubiCasa5K 的預訓練模型（Eden 從 Google Drive 下載權重檔上傳）。轉成 ONNX 後量化成 8 位元，69 MB → 30 MB，和原版相比房間類別 97% 的像素相同、牆的重疊率 0.92。
- 執行：ONNX Runtime Web（WebAssembly，單執行緒），只在勾選 AI 辨識時才載入，模型存在瀏覽器的 Cache Storage，不需要後端，圖片不會上傳。直接開 `index.html` 檔案時瀏覽器不允許下載模型，只能從網站使用。
- 接法：模型只取代「找牆像素」，之後一樣走向量化、門窗、房間、2D 校正。模型常把門窗也標成牆，所以先把門窗像素挖掉，牆上才有缺口。規則找不到開門弧或窗線的缺口再問模型（混合判斷）。
- 為了讓模型的牆封得起來，另外加了：水平、垂直牆分開找（避免牆角色塊把牆撐厚）、柱子、牆角延伸接合。門窗辨識也修了一個重複的情況：兩段緊貼的平行牆會在同一個位置各找到一次窗。
- 真實彩色格局圖（第 12 節那張）：一般辨識 7 門 2 窗、6 個房間（陽台沒封起來）；AI 辨識 8 門 2 窗、5 個房間：7 扇真的門都找到，另外把玄關通道當成一扇門（假門）；左下兩間衛浴與左側臥室都封起來了，客廳、中間臥室自動命名。右上臥室與陽台因為圖片右邊被裁掉、外牆沒畫出來，還是沒封起來。
- 範例圖：黑白範例 4 個房間、4 門 2 窗；彩色範例的主臥下牆有一段模型沒認出來，和客餐廳連成一間。合成範例的細門弧模型比較容易漏，所以門窗保留規則優先。
- 模型在 Chrome 無頭模式下一張圖約 7 秒（沒有 GPU、單執行緒），一般電腦會快很多。
- 授權：CC BY-NC 4.0，只能非商業使用。之後若要收費，要用使用者在 2D 校正修正過的圖面自己訓練（或微調）一個可商用的模型。

## 18. 外牆封不起來（2026-10-03）
Eden 請我整理還能優化的地方，再從第 1 項開始做。第 1 項是第 12、16、17 節都留下的問題：真實格局圖右上臥室和右側陽台封不起來。
- 原因：右上臥室的上方被圖片裁掉；陽台外側只畫一條很細的灰線（欄杆），一般辨識和模型都不認為是牆。
- 做法（`FPVectorize.closeOuter`，門窗辨識之後執行）：牆的末端沒接到別的牆時，順著牆的方向往前找 6 公尺內第一面橫過來的牆（差 0.5 公尺內也算碰到）。只有延伸線的其中一側一直到圖片邊緣都沒有牆，也就是房子的外緣，才延伸接上；室內隔間牆的開放通道兩側都有房間，不會被接起來。放在門窗之後，避免把窗戶旁邊的缺口當成外牆補掉。
- AI 辨識另外把「牆碰到圖片邊緣」的判斷放寬到 0.25 公尺（模型的牆在邊緣常差幾個像素），右上臥室上方會補一面外牆。
- 結果：一般辨識 6 → 7 個房間（多了陽台）、AI 辨識 5 → 7 個房間（多了右上臥室和陽台），兩種都是整間每個空間都封起來，AI 還把陽台、兩間臥室自動命名。門窗數量不變。黑白範例、彩色範例的一般辨識不變；PDF 施工圖不經過這一步。

## 19. 自動推算比例（2026-10-03）
優化清單第 2 項。建商格局圖通常沒有標尺寸，原本辨識時用「圖面實際寬度」的預設值，房間面積和家具大小都不對，要使用者自己用比例尺量。
- 做法（`FPOpenings.scaleFromDoors`）：找到的門洞寬度（像素）取中位數當作 90 公分，換算每公尺幾個像素，再用新的比例重新辨識一次（門窗缺口的寬度範圍、接牆的距離都依比例換算）。至少要找到 2 扇門才推算。
- 只用在新上傳的圖片：範例圖已知寬度、PDF 由使用者填比例、使用者自己改過「圖面實際寬度」之後都不再推算。AI 辨識時等模型跑完，用模型的門推算。
- 準確度：黑白範例推算 12.8 公尺，實際 13.6 公尺（差 6%）。真實格局圖推算 15.0 公尺（一般辨識）、15.5 公尺（AI 辨識），沒有實際尺寸可以對照。辨識結果會跳出提示，請使用者有已知尺寸時用比例尺確認。
- 順便修正：AI 辨識的柱子大小上限原本是 1.6 公尺，比例一變就會漏掉真實格局圖客廳角落的柱子、客廳封不起來，放寬到 2.5 公尺後，比例在每公尺 42–55 像素之間結果都穩定。
